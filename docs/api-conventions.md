# API Conventions

## REST Principles

The API follows RESTful design principles.

- Use nouns for resource names.
- Use plural resource names.
- Keep URLs lowercase.
- Do not include verbs in endpoint paths.

Examples:

GET    /products
GET    /products/{id}
POST   /products
PUT    /products/{id}
PATCH  /products/{id}
DELETE /products/{id}

---

## HTTP Methods

GET

- Retrieve resources.
- Must not modify data.

POST

- Create a new resource.

PUT

- Replace an existing resource.

PATCH

- Partially update a resource.

DELETE

- Remove a resource.

---

## Status Codes

Use standard HTTP status codes.

200 OK

Successful request.

201 Created

Resource created successfully.

204 No Content

Successful request without response body.

400 Bad Request

Invalid request.

401 Unauthorized

Authentication required.

403 Forbidden

Authenticated but not allowed.

404 Not Found

Resource not found.

409 Conflict

Business conflict (duplicate resource, etc.).

422 Unprocessable Entity

Validation error.

500 Internal Server Error

Unexpected server error.

---

## Request Validation

- Validate all input using Pydantic schemas.
- Do not manually validate request bodies inside routers.
- Use query parameter validation provided by FastAPI whenever possible.

---

## Response Models

- Always return response models.
- Do not expose SQLAlchemy models directly.
- Keep responses consistent.

---

## Error Responses

Business errors should be raised as custom exceptions.

HTTP responses should be generated by global exception handlers.

---

## Pagination

Collection endpoints should support pagination when appropriate.

Recommended parameters:

- skip
- limit

---

## Filtering

Filtering should use query parameters.

Example:

GET /products?category=electronics

---

## Sorting

Sorting should use query parameters.

Example:

GET /products?sort_by=name&order=asc

---

## Naming

Use descriptive names.

Examples:

products
categories
orders

Avoid abbreviations whenever possible.

---

## Versioning

The initial version does not expose API versioning.

Future versions may adopt:

/api/v1/
/api/v2/

without breaking existing clients.
